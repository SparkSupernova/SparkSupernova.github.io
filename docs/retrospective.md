# Project Retrospective

## What Went Well

The strongest part of this project was the decision to treat public information
as an evidence boundary. My work is difficult to summarize because
NovaLiveSystem is much larger than a normal classroom website, and much of its
architecture is intentionally private. Instead of trying to compress the whole
system into two pages, I used the public SparkPlugged website, GitHub showcase,
and professional profiles as the source of truth. That kept the portfolio
accurate and made the content easier for a general audience to understand.

The technical structure also stayed coherent. The homepage and About page use
semantic HTML, the same external stylesheet, and consistent navigation. I built
the visual system once and extended it rather than making the second page feel
like a separate project. The repository history tells a logical story from
structure to styling, documentation, and final expansion. That progression is
more useful than a single upload because it makes the work inspectable.

The scope boundary worked. My original course charter warned that I tend to
overscope small assignments because I normally work with complex systems. For
this project, I kept authentication, databases, dynamic features, additional
pages, and private technical detail out of the build. The result is still
distinctly mine without becoming another full SparkPlugged platform.

## What Went Wrong

The largest failure was schedule control. I fell behind in the course and began
this project too close to the final deadline. That turned an assignment designed
to demonstrate planned project management into a recovery operation. The
website was completed, but the compressed schedule removed the normal space for
feedback, gradual revision, and early testing.

My earlier project artifacts were also incomplete or unavailable. The final
scope was supposed to incorporate formal peer feedback, but no peer-feedback
artifact was present when I assembled the repository. Inventing feedback would
have made the document look complete while weakening its integrity, so I stated
the limitation directly and revised against the charter and rubric instead.
That was the honest decision, but it also exposed a continuity problem in how I
managed course files.

The first local preview workflow was not as reliable as expected, so source
validation and the deployed GitHub Pages site became the main verification
points. The final deployment succeeded, but a better project schedule would
have included browser testing at multiple viewport sizes before publication
rather than concentrating verification at the end.

## What I Would Do Differently

I would begin by creating the repository and documentation structure during the
first week, even if the files contained only headings. That would give every
assignment a durable destination and prevent the scope statement, peer review,
and final reflection from becoming disconnected artifacts.

I would also convert the WBS into small weekly commitments. “Build the website”
is too large to manage honestly. Separate commitments for content evidence,
semantic structure, responsive styling, accessibility, documentation, and
deployment would make delay visible earlier. A short status review after each
commit would show whether the project was still aligned with its scope and
deadline.

Finally, I would request feedback on one question at a time. A general request
to “review my portfolio” can produce vague reactions. Asking whether a
nontechnical visitor can explain my work after reading the hero section, or
whether the boundary between public research and private implementation is
clear, would generate feedback I could act on.

## Actionable Lessons

1. Create the final repository structure at project initiation, not at project
   closure.
2. Store every course artifact in the same project path as soon as it is
   created.
3. Treat public-source verification as a formal content task.
4. Freeze optional features when the critical path is threatened.
5. Test each page at desktop and mobile widths before deployment.
6. Ask reviewers focused questions tied to acceptance criteria.
7. Preserve honest limitations instead of manufacturing evidence that a
   requirement was completed.

The project succeeded technically, but the process showed that recovery skill
is not the same thing as schedule control. The next improvement is not to work
faster under pressure. It is to make project state visible early enough that the
pressure does not become the management system.
